Definition of done:

- Freelancer cannot start before confirmed funding.
- A repeated request cannot produce two checkout/payment transactions.
- Timeout cannot be treated as a definite failure.
- All backend tests pass without frontend changes.

Current implementation contract: simulated capture/ledger, `Milestone=FUNDED` and `Job=IN_PROGRESS` on confirmation. The Client uses the saved bank account under `paymentMethodId=BANK_ACCOUNT_ON_FILE`. The earlier generic `paymentMethodId=pm_...` example in the functional spec does not exist yet. Checkout is captured at funding; the legacy approval path's second capture is now idempotent at Payment. Release orchestration remains step 4.

- [ ] On the Client job detail in `frontend/src/Workflow.tsx`, when `job.status=AWAITING_PAYMENT` and `job.contract.status=PENDING_FUNDING`, show the immutable contract amount/currency, deliverables, acceptance criteria, delivery deadline, review window, revision limit, and a clear **mô phỏng** label. - [ ] POST `/api/v1/contracts/{contractId}/milestones/{milestoneId}/fund` with header `Idempotency-Key: <random UUID>` and body `{"paymentMethodId":"BANK_ACCOUNT_ON_FILE","expectedAmount":{"amount":"500.00","currency":"USD"}}`. The amount must come from `Job.contract.amount`, formatted as a decimal string with two places; do not calculate from an editable form field. The API returns the existing `ResponseAPI` envelope with `data: {fundingTransactionId,fundingStatus,simulation,providerReference,nextAction,retryAfterSeconds}`.
- [ ] Generate one key per user funding attempt and keep it through double-clicks, auth refresh, network errors, and page reloads (scoped by Client + contract + milestone, e.g. sessionStorage). Never mint a new key just because the POST timed out. Remove it only after `SUCCEEDED` or a definitive `FAILED`; a new attempt after `FAILED` requires a new key.
- [ ] On initial load and after an uncertain POST, call `GET /api/v1/contracts/{contractId}/milestones/{milestoneId}/fund` for the latest transaction (`data=null` means no attempt). If a transaction ID is known, `GET .../fund/{fundingTransactionId}` reads that exact attempt. Poll at `retryAfterSeconds` for `PENDING`, `PROCESSING`, `UNKNOWN` with cleanup on unmount and bounded intervals. Keep funding disabled while unresolved; show “đang đối soát” for `UNKNOWN`, never “thất bại chắc chắn”.

#### B. Submission/review handoff — implement after funding UI

URL deliverable bắt buộc là HTTPS; acceptance evidence cần note hoặc HTTPS URL; ít nhất một bằng chứng. Không cho chọn ID ngoài contract snapshot hoặc gửi trùng cùng ID trong một submission.

Sau lỗi mạng, gọi `GET /api/v1/contracts/{contractId}/submissions` trước khi cân nhắc gửi lại; không tự tăng version ở frontend.
- [ ] GET `/api/v1/contracts/{contractId}/submissions` trả mảng theo version tăng dần. Dùng phần tử cuối làm bản mới nhất; mỗi item có `{id,contractId,milestoneId,freelancerId,version,status,summary,submittedAt,submittedLate,reviewDueAt,reviewGraceDueAt,reviewedAutomatically,disputeId,reviewerFeedback,reviewCriterionIds,reviewDeliverableIds,deliverables,acceptanceEvidence}`. Mỗi phần tử evidence trả `{requirementId,description,url}`; với `acceptanceEvidence`, `requirementId` chính là criterion ID. Hiển thị bằng chứng theo từng requirement/criterion, marker nộp muộn, thời hạn review (UTC đổi sang múi giờ người dùng), lịch sử các version và feedback; không render HTML thô từ summary/note, mở link ngoài với `rel="noopener noreferrer"`.
- [ ] Client chỉ hiển thị review controls khi bản cuối `status=SUBMITTED` và `job.contract.status=UNDER_REVIEW` / `milestoneStatus=SUBMITTED`. POST `/api/v1/contracts/{contractId}/submissions/{submissionId}/decisions` với `{ "decision":"APPROVE", "note":"..." }`, `{ "decision":"REQUEST_REVISION", "feedback":"...", "criterionIds":["..."], "deliverableIds":[] }`, hoặc `{ "decision":"OPEN_DISPUTE", "reasonCode":"QUALITY", "description":"..." }`. Revision cần feedback và ít nhất một ID liên quan; dispute cần `reasonCode` không rỗng (tối đa 60 ký tự) và `description` không rỗng (tối đa 10.000 ký tự). Dùng ID từ contract snapshot. - [ ] Sau `APPROVE` (thủ công hoặc tự động), UI hiển thị `milestoneStatus=RELEASE_PENDING`, **chưa** hiển thị “đã giải ngân/hoàn thành”; worker release thuộc mục 4. Sau `OPEN_DISPUTE`, submission/milestone/contract là `DISPUTED`, response có `disputeId`; khóa nút review/nộp tiếp, hiển thị trạng thái chờ Admin. Backend Admin resolution và evidence timeline vẫn thuộc mục 6.
- [ ] Bổ sung test API/UI cho form evidence hợp lệ/thiếu/sai URL, giữ key khi retry, nộp muộn, lịch sử version, giới hạn revision, Client/Freelancer visibility, stale submission `409`, double-click quyết định, và trạng thái `RELEASE_PENDING` không bị nhầm là đã thanh toán.

Request/decision/worker use the same milestone row lock as submission/approval/settlement. Any existing settlement record (including PROCESSING/UNKNOWN/SUCCEEDED), active dispute or stale submission blocks ordinary cancellation. The refund claim prevents submission and settlement preparation/release. Payment additionally prevents both release and refund at the checkout boundary. Legacy OPEN cancel now rejects every contract-backed Job with existing `CONTRACT_API_REQUIRED`; assignment and legacy cancel share a Job row lock so a delayed OPEN cancel cannot overwrite a newly assigned contract.

**Reconciliation:** always GET the stored refund key first. Specifically absent → POST original persisted key/checkout/amount/currency; never generate a fresh key. Verify provider identity/payer/amount/currency/simulation/reference before applying success. Timeout/5xx/408 or unavailable/malformed/mismatched lookup → UNKNOWN, keep Job IN_PROGRESS / Contract ACTIVE / Milestone REFUND_PENDING and do not claim refund complete. POST 429 → FAILED_RETRYABLE; definitive POST 4xx → FAILED with retry paused. Existing unresolved provider record is reconciled by lookup, never duplicated; provider FAILED retryability is preserved. Remote success + lost response/local commit is recovered with the same committed identity. Local DB failures roll back rather than becoming definitive provider failures. Scheduler waits 30 seconds, handles at most 50 due rows, logs only record IDs on retry failure and reuses the same worker after restart.

**Success transitions / notifications:** definitive validated refund SUCCEEDED → cancellation CANCELLED, milestone REFUNDED, Contract CANCELLED, Job CANCELLED, retry stopped. Pre-funding has nullable refundStatus/reference. Notifications use existing infrastructure for proposal, rejection, refund pending and confirmation. Confirmed refund explicitly means Client simulated ledger restored, not money transferred back to a real bank. No outbox platform or Step 6 implementation was added.
