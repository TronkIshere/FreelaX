Definition of done:

- Freelancer cannot start before confirmed funding.
- A repeated request cannot produce two checkout/payment transactions.
- Timeout cannot be treated as a definite failure.
- All backend tests pass without frontend changes.

Current implementation contract: simulated capture/ledger, `Milestone=FUNDED` and `Job=IN_PROGRESS` on confirmation. The Client uses the saved bank account under `paymentMethodId=BANK_ACCOUNT_ON_FILE`. The earlier generic `paymentMethodId=pm_...` example in the functional spec does not exist yet. Checkout is captured at funding; the legacy approval path's second capture is now idempotent at Payment. Release orchestration remains step 4.

### Frontend handoff — implement in `frontend/` after backend funding verification

> This checklist is planning only; the backend-only scope rule above still applies. Do not mark frontend items done until their code and tests are complete.

#### A. Immediately required to make assigned jobs usable

- [ ] Add typed API methods and types in `frontend/src/api.ts` and `frontend/src/types.ts` for funding and Client bank setup. Existing `api.assign` and `Job.contract` supply the contract/milestone IDs; guard against a null `contract` or `milestoneId`.
- [ ] Add Client bank setup UI using `GET/PUT /api/v1/payment-methods/bank-account`. `GET` returns `{paymentMethodId:"BANK_ACCOUNT_ON_FILE",ready,bankCode,maskedAccountNumber}`. `PUT` body is `{bankCode,bankAccountNumber,bankAccountHolderName}`; require 6–34 digits for account number and a holder name. Show only the masked response after saving. Do not put the full account number in URL, analytics, localStorage, error text, or page logs. Client registration currently omits bank details, so this UI is necessary for existing/new Client accounts.
- [ ] On the Client job detail in `frontend/src/Workflow.tsx`, when `job.status=AWAITING_PAYMENT` and `job.contract.status=PENDING_FUNDING`, show the immutable contract amount/currency, deliverables, acceptance criteria, delivery deadline, review window, revision limit, and a clear **mô phỏng** label. Show the funding action only to the Client owner; Freelancer sees a waiting state. Require explicit confirmation of amount before POST.
- [ ] POST `/api/v1/contracts/{contractId}/milestones/{milestoneId}/fund` with header `Idempotency-Key: <random UUID>` and body `{"paymentMethodId":"BANK_ACCOUNT_ON_FILE","expectedAmount":{"amount":"500.00","currency":"USD"}}`. The amount must come from `Job.contract.amount`, formatted as a decimal string with two places; do not calculate from an editable form field. The API returns the existing `ResponseAPI` envelope with `data: {fundingTransactionId,fundingStatus,simulation,providerReference,nextAction,retryAfterSeconds}`.
- [ ] Generate one key per user funding attempt and keep it through double-clicks, auth refresh, network errors, and page reloads (scoped by Client + contract + milestone, e.g. sessionStorage). Never mint a new key just because the POST timed out. Remove it only after `SUCCEEDED` or a definitive `FAILED`; a new attempt after `FAILED` requires a new key.
- [ ] On initial load and after an uncertain POST, call `GET /api/v1/contracts/{contractId}/milestones/{milestoneId}/fund` for the latest transaction (`data=null` means no attempt). If a transaction ID is known, `GET .../fund/{fundingTransactionId}` reads that exact attempt. Poll at `retryAfterSeconds` for `PENDING`, `PROCESSING`, `UNKNOWN` with cleanup on unmount and bounded intervals. Keep funding disabled while unresolved; show “đang đối soát” for `UNKNOWN`, never “thất bại chắc chắn”.
- [ ] Map `SUCCEEDED` to refresh `api.job(jobId)` and unlock the Freelancer workflow; map `FAILED` to a retry action with a fresh key; map `409` amount/state/key conflicts to a job and funding-status refresh. On missing bank (`4021`/422), direct Client to bank setup. On `401`, rely on existing token refresh while retaining the same key. Preserve actionable server error text, but do not display raw bank details.
- [ ] In `frontend/src/Finance.tsx`, avoid calling the existing `/api/v1/marketplace/jobs/{jobId}/payment-status` for unfunded jobs: it currently returns `409 JOB_NOT_PAID`. Render the funding status instead; use payment-status only after `SUCCEEDED` / checkout ID exists. Show simulated capture separately from later release/off-ramp/tax progress.
- [ ] Update `frontend/src/Workflow.test.tsx`, `frontend/src/api.test.ts`, and finance tests for Client/Freelancer visibility, missing bank, double-click, network timeout, reload with same key, `UNKNOWN` polling, `FAILED` retry, and success refresh. Ensure no test assumes assigning a Freelancer starts work immediately.

#### B. Submission/review handoff — implement after funding UI

- [ ] Replace `api.submitWork`, `api.submissions`, `api.requestRevision`, and `api.approveWork` in `frontend/src/api.ts`/`frontend/src/WorkLifecycle.tsx` for contract-backed jobs. The old `/api/v1/marketplace/jobs/{jobId}/submit-work`, `/request-revision`, and `/approve` now return `409` with numeric error `4029 CONTRACT_API_REQUIRED` when a contract exists; keeping those buttons wired to the old endpoints will block the current UI after funding.
- [ ] Use `job.contract.id`, `job.contract.milestoneId`, and the contract snapshot's `deliverables[]` / `acceptanceCriteria[]` IDs. POST `/api/v1/contracts/{contractId}/submissions` as Freelancer with `Idempotency-Key: <UUID>` and body such as `{"summary":"Đã hoàn tất","deliverables":[{"requirementId":"<deliverable ID>","url":"https://...","description":"Link source và hướng dẫn"}],"acceptanceEvidence":[{"criterionId":"<criterion ID>","note":"Đã kiểm tra responsive","url":"https://..."}]}`. URL deliverable bắt buộc là HTTPS; acceptance evidence cần note hoặc HTTPS URL; ít nhất một bằng chứng. Không cho chọn ID ngoài contract snapshot hoặc gửi trùng cùng ID trong một submission.
- [ ] Giữ nguyên idempotency key **và bản draft payload đi cùng key** của một lần bấm Gửi qua double-click, refresh token, mất mạng và reload; cùng key + cùng payload trả lại cùng submission, cùng key + payload khác trả `409/4026`. Sau lỗi mạng, gọi `GET /api/v1/contracts/{contractId}/submissions` trước khi cân nhắc gửi lại; không tự tăng version ở frontend.
- [ ] GET `/api/v1/contracts/{contractId}/submissions` trả mảng theo version tăng dần. Dùng phần tử cuối làm bản mới nhất; mỗi item có `{id,contractId,milestoneId,freelancerId,version,status,summary,submittedAt,submittedLate,reviewDueAt,reviewGraceDueAt,reviewedAutomatically,disputeId,reviewerFeedback,reviewCriterionIds,reviewDeliverableIds,deliverables,acceptanceEvidence}`. Mỗi phần tử evidence trả `{requirementId,description,url}`; với `acceptanceEvidence`, `requirementId` chính là criterion ID. Hiển thị bằng chứng theo từng requirement/criterion, marker nộp muộn, thời hạn review (UTC đổi sang múi giờ người dùng), lịch sử các version và feedback; không render HTML thô từ summary/note, mở link ngoài với `rel="noopener noreferrer"`.
- [ ] Client chỉ hiển thị review controls khi bản cuối `status=SUBMITTED` và `job.contract.status=UNDER_REVIEW` / `milestoneStatus=SUBMITTED`. POST `/api/v1/contracts/{contractId}/submissions/{submissionId}/decisions` với `{ "decision":"APPROVE", "note":"..." }`, `{ "decision":"REQUEST_REVISION", "feedback":"...", "criterionIds":["..."], "deliverableIds":[] }`, hoặc `{ "decision":"OPEN_DISPUTE", "reasonCode":"QUALITY", "description":"..." }`. Revision cần feedback và ít nhất một ID liên quan; dispute cần `reasonCode` không rỗng (tối đa 60 ký tự) và `description` không rỗng (tối đa 10.000 ký tự). Dùng ID từ contract snapshot. Hiển thị `revisionsUsed/maxRevisions`; khi hết lượt, tắt hẳn revision nhưng vẫn cho Client duyệt hoặc mở dispute. `409/4027` nghĩa là bản đã cũ hoặc đã được quyết định: tải lại job và submissions, không gửi quyết định vào ID cũ; `409/4028` nghĩa là đã hết lượt sửa; `409/4031` nghĩa là dispute đã mở; `422/4032` nghĩa là thiếu lý do dispute.
- [ ] Sau `APPROVE` (thủ công hoặc tự động), UI hiển thị `milestoneStatus=RELEASE_PENDING`, **chưa** hiển thị “đã giải ngân/hoàn thành”; worker release thuộc mục 4. Dùng `reviewedAutomatically` để ghi rõ nguồn quyết định, không suy đoán theo đồng hồ. Sau `REQUEST_REVISION`, milestone trở lại `IN_PROGRESS`, contract `REVISION`, job `REVISION_REQUESTED`; Freelancer có thể nộp version mới. Sau `OPEN_DISPUTE`, submission/milestone/contract là `DISPUTED`, response có `disputeId`; khóa nút review/nộp tiếp, hiển thị trạng thái chờ Admin. Backend Admin resolution và evidence timeline vẫn thuộc mục 6.
- [ ] Bổ sung test API/UI cho form evidence hợp lệ/thiếu/sai URL, giữ key khi retry, nộp muộn, lịch sử version, giới hạn revision, Client/Freelancer visibility, stale submission `409`, double-click quyết định, và trạng thái `RELEASE_PENDING` không bị nhầm là đã thanh toán.

#### C. Next stages needed for full MVP UI — backend APIs in sections 3–9 are still incomplete

- [ ] **Review deadlines (step 3):** lấy `reviewDueAt` từ backend (mặc định 72 giờ sau `submittedAt` theo contract review window đã snapshot), hiển thị countdown theo giờ địa phương nhưng dùng timestamp UTC gốc. Khi chưa có field này, có thể giải thích chính sách +24h từ amount/`reviewDueAt`, nhưng phải đồng bộ lại trạng thái từ backend; không cho browser tự quyết định. Test chính xác biên `500.00`/`500.01`, mốc 72h/96h, late scheduler, tranh chấp, và manual-vs-auto race.
- [ ] **Release (step 4):** separate “Client approved” from `RELEASE_PENDING` and `RELEASED`. In Finance, show independent primary payment, Solana evidence, off-ramp, and MISA/tax states with separate retry/pending/error text. - [ ] **Cancellation/refund (step 5):** show immediate cancellation before funding, policy/consent flow after funding but before work, and dispute entry during work/review when consent is absent. Show refund as pending until backend confirms; disable cancel after release/refund starts. Repeated clicks reuse the same mutation key.
- [ ] **Dispute/Admin (step 6):** provide participant dispute opening with reason and append-only evidence links; show immutable contract criteria, every submission, feedback and audit timeline. Disable repeat resolution while financial execution is pending; never let the UI select partial amounts in MVP.
- [ ] **Shared API/UI behavior (step 7):** handle server `allowedActions` when available, machine-readable `code`, `retryable`, `requestId`, and `currentState` once the planned error envelope replaces today's numeric `status/error`. Preserve decimal precision in requests, refresh on optimistic-lock `409`, avoid duplicate mutation keys across different payloads, and keep role guards mirrored by backend authorization. Show notifications from committed backend events and preserve a useful loading/empty/error state for each async view.
- [ ] **Profiles/portfolio (step 8):** add public profile and private `/me` editor, Client company fields, Freelancer skills and up to 12 portfolio items with HTTPS URLs, and explicit manual/simulated verification badges. Public views must mask bank/tax/identity/wallet data. Show `rating=null` as “chưa có đánh giá”, not zero stars; render reputation counts and `calculatedAt` from backend data.
- [ ] **Two-sided ratings (step 9):** after eligible completion, show one invitation per participant, a private draft/submit state, and hidden content until both reviews arrive or the 14-day window ends. Never show an ineligible review action on cancelled/refunded contracts. Support moderation status without silently editing previously published text.
