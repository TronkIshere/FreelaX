Definition of done:

- Freelancer cannot start before confirmed funding.
- A repeated request cannot produce two checkout/payment transactions.

- All backend tests pass without frontend changes.

Current implementation contract: simulated capture/ledger, `Milestone=FUNDED` and `Job=IN_PROGRESS` on confirmation. The Client uses the saved bank account under `paymentMethodId=BANK_ACCOUNT_ON_FILE`. The earlier generic `paymentMethodId=pm_...` example in the functional spec does not exist yet. Checkout is captured at funding; the legacy approval path's second capture is now idempotent at Payment. Release orchestration remains step 4.

#### A. Immediately required to make assigned jobs usable

Client registration currently omits bank details, so this UI is necessary for existing/new Client accounts.
- [ ] On the Client job detail in `frontend/src/Workflow.tsx`, when `job.status=AWAITING_PAYMENT` and `job.contract.status=PENDING_FUNDING`, show the immutable contract amount/currency, deliverables, acceptance criteria, delivery deadline, review window, revision limit, and a clear **mô phỏng** label. Show the funding action only to the Client owner; Freelancer sees a waiting state. Require explicit confirmation of amount before POST.
- [ ] POST `/api/v1/contracts/{contractId}/milestones/{milestoneId}/fund` with header `Idempotency-Key: <random UUID>` and body `{"paymentMethodId":"BANK_ACCOUNT_ON_FILE","expectedAmount":{"amount":"500.00","currency":"USD"}}`. The amount must come from `Job.contract.amount`, formatted as a decimal string with two places; do not calculate from an editable form field. The API returns the existing `ResponseAPI` envelope with `data: {fundingTransactionId,fundingStatus,simulation,providerReference,nextAction,retryAfterSeconds}`.
- [ ] Generate one key per user funding attempt and keep it through double-clicks, auth refresh, network errors, and page reloads (scoped by Client + contract + milestone, e.g. sessionStorage). Never mint a new key just because the POST timed out. Remove it only after `SUCCEEDED` or a definitive `FAILED`; a new attempt after `FAILED` requires a new key.
- [ ] On initial load and after an uncertain POST, call `GET /api/v1/contracts/{contractId}/milestones/{milestoneId}/fund` for the latest transaction (`data=null` means no attempt). If a transaction ID is known, `GET .../fund/{fundingTransactionId}` reads that exact attempt. Poll at `retryAfterSeconds` for `PENDING`, `PROCESSING`, `UNKNOWN` with cleanup on unmount and bounded intervals. Keep funding disabled while unresolved; show “đang đối soát” for `UNKNOWN`, never “thất bại chắc chắn”.
- [ ] Map `SUCCEEDED` to refresh `api.job(jobId)` and unlock the Freelancer workflow; map `FAILED` to a retry action with a fresh key; map `409` amount/state/key conflicts to a job and funding-status refresh. #### B. Submission/review handoff — implement after funding UI

URL deliverable bắt buộc là HTTPS; acceptance evidence cần note hoặc HTTPS URL; ít nhất một bằng chứng. Không cho chọn ID ngoài contract snapshot hoặc gửi trùng cùng ID trong một submission.
- [ ] Giữ nguyên idempotency key **và bản draft payload đi cùng key** của một lần bấm Gửi qua double-click, refresh token, mất mạng và reload; cùng key + cùng payload trả lại cùng submission, cùng key + payload khác trả `409/4026`. Sau lỗi mạng, gọi `GET /api/v1/contracts/{contractId}/submissions` trước khi cân nhắc gửi lại; không tự tăng version ở frontend.
- [ ] GET `/api/v1/contracts/{contractId}/submissions` trả mảng theo version tăng dần. Dùng phần tử cuối làm bản mới nhất; mỗi item có `{id,contractId,milestoneId,freelancerId,version,status,summary,submittedAt,submittedLate,reviewDueAt,reviewGraceDueAt,reviewedAutomatically,disputeId,reviewerFeedback,reviewCriterionIds,reviewDeliverableIds,deliverables,acceptanceEvidence}`. Mỗi phần tử evidence trả `{requirementId,description,url}`; với `acceptanceEvidence`, `requirementId` chính là criterion ID. Hiển thị bằng chứng theo từng requirement/criterion, marker nộp muộn, thời hạn review (UTC đổi sang múi giờ người dùng), lịch sử các version và feedback; không render HTML thô từ summary/note, mở link ngoài với `rel="noopener noreferrer"`.
- [ ] Client chỉ hiển thị review controls khi bản cuối `status=SUBMITTED` và `job.contract.status=UNDER_REVIEW` / `milestoneStatus=SUBMITTED`. POST `/api/v1/contracts/{contractId}/submissions/{submissionId}/decisions` với `{ "decision":"APPROVE", "note":"..." }`, `{ "decision":"REQUEST_REVISION", "feedback":"...", "criterionIds":["..."], "deliverableIds":[] }`, hoặc `{ "decision":"OPEN_DISPUTE", "reasonCode":"QUALITY", "description":"..." }`. Revision cần feedback và ít nhất một ID liên quan; dispute cần `reasonCode` không rỗng (tối đa 60 ký tự) và `description` không rỗng (tối đa 10.000 ký tự). Dùng ID từ contract snapshot. - [ ] Sau `APPROVE` (thủ công hoặc tự động), UI hiển thị `milestoneStatus=RELEASE_PENDING`, **chưa** hiển thị “đã giải ngân/hoàn thành”; worker release thuộc mục 4. Sau `REQUEST_REVISION`, milestone trở lại `IN_PROGRESS`, contract `REVISION`, job `REVISION_REQUESTED`; Freelancer có thể nộp version mới. Sau `OPEN_DISPUTE`, submission/milestone/contract là `DISPUTED`, response có `disputeId`; khóa nút review/nộp tiếp, hiển thị trạng thái chờ Admin. Backend Admin resolution và evidence timeline vẫn thuộc mục 6.
- [ ] Bổ sung test API/UI cho form evidence hợp lệ/thiếu/sai URL, giữ key khi retry, nộp muộn, lịch sử version, giới hạn revision, Client/Freelancer visibility, stale submission `409`, double-click quyết định, và trạng thái `RELEASE_PENDING` không bị nhầm là đã thanh toán.

### 4. Release and settlement orchestration

#### Step 4.0 — Payment primary release primitive: IMPLEMENTED (2026-10-05)

Payment now has an internal, atomic **simulated USD entitlement credit**. This is not real escrow, a bank transfer, Solana payment, off-ramp or tax completion. Backend Step 4 remains pending Marketplace orchestration; the checkboxes below are not complete.

**Internal API** — existing `X-Internal-Api-Key` service protection, no new public/browser route or CORS allowance:

- `POST /internal/BofA/payout/releases`
- `GET /internal/BofA/payout/releases/by-key?releaseKey=<URL-encoded server key>`
- `GET /internal/BofA/payout/releases/by-checkout/{checkoutOrderId}`

POST body (illustrative IDs/key, not runtime credentials):

```json
{
  "checkoutOrderId": "00000000-0000-0000-0000-000000000001",
  "recipientUserId": "00000000-0000-0000-0000-000000000002",
  "expectedAmount": { "amount": "500.00", "currency": "USD" },
  "releaseKey": "marketplace-release-<milestoneId>"
}
```

The future Marketplace orchestrator must verify approval, confirmed funding, contract/milestone ownership and absence of an open dispute; derive the assigned Freelancer UUID and stable release key on the server. Payment does not have Marketplace's role/assignment data. It checks checkout existence, `CAPTURED`, exact captured `amountUsd`, implicit checkout currency `USD`, recipient different from payer, and idempotency. Amount is positive, max 17 integer digits and 2 decimal places; key is nonblank, at most 100 characters, with no surrounding whitespace.

POST and both GETs return the existing numeric `ResponseAPI` envelope:

```json
{
  "code": 200,
  "data": {
    "releaseId": "00000000-0000-0000-0000-000000000003",
    "releaseKey": "marketplace-release-<milestoneId>",
    "checkoutOrderId": "00000000-0000-0000-0000-000000000001",
    "recipientUserId": "00000000-0000-0000-0000-000000000002",
    "status": "SUCCEEDED",
    "amount": "500.00",
    "currency": "USD",
    "simulation": true,
    "releaseReference": "sim-release-00000000-0000-0000-0000-000000000003",
    "retryable": false,
    "createdAt": "2026-10-05T08:00:00Z",
    "updatedAt": "2026-10-05T08:00:00Z"
  }
}
```

**Persistence/atomicity:** `bofa_payout_releases` is unique by `release_key` and by `checkout_order_id`. `bofa_recipient_credits` has one immutable credit per release ID and unique checkout, with recipient/currency indexing. The summed entries are the user's credited USD entitlement, starting at zero; they do not change the legacy bank ledger or its artificial opening balance. A pessimistic checkout lock, release insertion, credit insertion and `SUCCEEDED` update share one DB transaction. Failure/rollback leaves neither release nor credit. No capture, debit, checkout creation or provider network call occurs.

**Idempotency:** same key + same canonical checkout/recipient/amount/currency returns the same release/latest stored state. Equivalent decimal scales normalize to 2 places. A changed payload returns `409/3014 RELEASE_KEY_CONFLICT`. A different key for an already reserved/released checkout returns `409/3009 PAYOUT_ALREADY_RELEASED` without another credit. Global key collisions across checkout locks are rejected after the losing transaction rolls back.

**Lookup/reconciliation:** GET is read-only; no record returns `404/3008`. After an HTTP timeout/lost response, query by key and checkout before resending the exact request with the same key. A committed operation is returned, while a rolled-back operation has no release/credit. Never mint a new key to handle uncertainty. There is no Payment worker or external provider in this primitive.

**Statuses:** `PENDING`, `PROCESSING`, `SUCCEEDED`, `FAILED`, `UNKNOWN`. Current local execution sets `PROCESSING` inside the atomic transaction and commits only `SUCCEEDED`; validation errors return immediately without creating a failed credit. It does not manufacture provider uncertainty. Reserved statuses support later contract evolution; no retry worker for them is implemented in Step 4.0. `retryable=false` indicates no independent provider retry action here; transport retries with the same key remain idempotent. `lastError` is a nullable persisted safe-text field, currently unused and not exposed. Response timestamps are UTC instants; no bank/tax/token/signer data or payload hash is returned.

**Errors:** existing envelopes retained. `400/1000` invalid input, `404/3004` missing checkout, `409/3005` not captured, `409/3012` amount mismatch, `409/3013` currency mismatch, `409/3014` key conflict, `409/3015` recipient equals payer, `409/3009` checkout already released. Missing/wrong internal API key returns the existing filter's HTTP 401.

**Validation/limits:** focused service tests use real Spring/JPA/H2 transactions, concurrent workers and injected failure after a flushed credit; controller tests use the actual internal-key filter. Existing funding checkout/capture tests remain part of the Payment test gate. H2 is test-only; real MySQL concurrency/HTTP integration and explicit production migrations remain pending. New JPA tables follow the existing `ddl-auto:update` demo convention. Marketplace, frontend, Solana, off-ramp and MISA remain unchanged.
